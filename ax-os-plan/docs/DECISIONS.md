### D-001 · 2026-10-17 · 제안 — Dental AX OS는 별도의 비공개 저장소에서 개발한다

- **상황**: 현재 저장소 `constant93/dental-homepage`는 **public**이며, `.github/workflows/pages.yml`이 `main` 브랜치의 루트 전체(`path: .`)를 GitHub Pages로 게시한다.
- **결정**: AX OS 코드는 새 **private** 저장소(예: `dental-ax-os`)에 만든다. 이 저장소에는 홈페이지만 둔다.
- **이유**: 운영 시스템의 코드·설정·향후 데이터 구조가 인터넷에 공개되면 안 된다. 실수로 seed/설정 파일이 Pages로 게시될 위험도 있다. 홈페이지와 운영 시스템은 배포 주기·보안 수준이 완전히 다르다.
- **결과**: 이 계획 문서는 임시로 `ax-os-plan/` 폴더(작업 브랜치)에 두고, private 저장소 생성 후 그 루트로 옮긴다. 이 브랜치는 `main`에 merge하지 않는다.

### D-002 · 2026-10-17 · 제안 — Modular Monolith

- **결정**: 앱 1개 + PostgreSQL 1개. 모듈은 `src/modules/*` 폴더로 구분.
- **이유**: 1개 병원, 소수 사용자, 소유자 1인 유지보수. Microservice는 운영 부담만 늘린다.
- **결과**: 모듈 간 호출은 함수 호출. 나중에 AI/분석만 Python 서비스로 떼어낼 수 있게 규칙 함수는 DB 조회와 계산을 분리해 둔다.

### D-003 · 2026-10-17 · 제안 — Next.js + TypeScript + Prisma + PostgreSQL

- **결정**: ARCHITECTURE.md A-3 표의 스택. 버전은 Sprint 1 시작 시 현재 안정 버전을 확인하고 이 문서에 기록.
- **이유**: 한 언어(TypeScript)로 화면과 서버. 자료가 많아 초보자 유지보수에 유리. Prisma schema는 테이블 구조를 한눈에 보여준다.
- **대안**: Remix/React Router, NestJS+React 분리, Drizzle ORM — 기능상 문제는 없으나 파일·개념 수가 늘거나 자료가 상대적으로 적음.

### D-004 · 2026-10-17 · 제안 — Phase 1 Daily Briefing은 LLM 없이 규칙 + 템플릿

- **결정**: "AI Daily Briefing" 영역은 Insight Engine 규칙 결과를 한국어 템플릿 문장으로 보여준다. LLM은 Phase 2.
- **이유**: (1) Mock 단계에서 외부 AI 비용·계약 불필요 (2) 환자정보 외부 전송 0 (3) 지어낸 내용이 나올 수 없음 (4) 규칙이 정확해야 LLM을 붙여도 정확하다.
- **결과**: 화면 이름은 "Daily Briefing". LLM이 붙으면 "AI" 표시를 추가한다.

### D-005 · 2026-10-17 · 제안 — 단일 병원 전용 (multi-tenant 아님)

- **결정**: `clinicId` 없이 설계.
- **이유**: 현재 목표는 한 병원의 운영 개선. SaaS화는 목표가 아니며, 미리 만들면 모든 쿼리가 복잡해진다.
- **결과**: 지점 확장 시 별도 결정 필요.

### D-006 · 미결정 — 운영 서버 위치 (Phase 2 Gate)

- **선택지**: (a) 병원 내부 서버/PC (b) 국내 리전 클라우드 (c) 혼합 — 내부에 import 에이전트, 클라우드에 앱
- **고려**: 환자정보 보관 위치, 백업·장애 대응을 누가 하는가, 원격 접속 필요 여부, 비용, DentWeb 데이터 접근 방법(내부망 필요 여부 — UNKNOWN)
- **결정 시점**: Phase 1 완료 후, DentWeb 연동 방법 확인 후.

### D-007 · 미결정 — 외부 LLM 사용 범위

- **고려**: 어떤 데이터가 외부로 나가는가(비식별 FACT만), 처리 위치(국외 전송 여부), 비용, 계약 조건, 법적 검토.
- **결정 시점**: Phase 2 시작 전. 원장 승인 필수.

### D-008 · 2026-10-17 · 제안 — 재고는 "사용 시 기록"이 아니라 "주간 실사" 기본

- **결정**: 일반 소모품은 주 1회 실사 수량으로 사용량을 계산. 고가 품목만 사용 시 기록.
- **이유**: 진료 중 사용 기록은 현장에서 지켜지지 않고, 지켜지지 않는 데이터는 AI 예측을 망친다. 적게 입력하되 꾸준한 데이터가 낫다.

### D-009 · 2026-10-17 · 제안 — 공급처 가격은 수동/명세서/CSV로만 수집

- **결정**: 공급처 사이트 scraping, 자동 로그인, 자동 주문을 구현하지 않는다.
- **이유**: 사이트 이용약관 위반 가능성, 계정 보안 위험, 사이트 변경 시 잦은 고장.
- **결과**: 입고 시 거래명세서 단가를 입력하면 가격 이력이 자연스럽게 쌓이도록 UI를 설계.
